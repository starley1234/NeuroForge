# Откуда берётся физика: простое объяснение

Три частых вопроса: откуда модель узнаёт про массу и прочность, надо ли чистить
базу от кривых моделей и что происходит при запросе. По порядку.

---

## 1. Четыре канала, по которым физика попадает в модель

Физику **никто не размечает руками**. Её считает наш движок: воксельная
геометрия + МКЭ на гексаэдрах. Дальше она входит в обучение четырьмя разными
способами — их полезно не путать.

```
   OpenSCAD код
        │
        ▼
  движок NEXUS ── считает: масса, центр масс, manifold, стенки, свесы, σ_max, запас
        │
        ├──(1)── текстом в обучающем примере:  <fem>{"mass_g":210,"safety_factor":3.1}
        ├──(2)── числом на общей шине:         invariants = [x,y,z, масса, Fx,Fy,Fz]
        ├──(3)── наградой в RL:                +1 компиляция, +1.5 manifold, +2 прочность
        └──(4)── фильтром качества:            плохое не попадает в корпус вообще
```

### Канал 1 — физика как текст (работает всегда)

Каждый обучающий пример выглядит так:

```
<task>Кронштейн под 350 Н, алюминий<scad>difference(){ ... }<fem>{"mass_g":210.4,
"sigma_max_mpa":89.1,"safety_factor":3.1,"min_wall_mm":2.4}
```

Модель учится продолжать эту последовательность, то есть предсказывать не только
код, но и его физические последствия. Так она постепенно связывает «толщина 2 мм
при 350 Н» с «запас 0.8» — то есть учится физике на примерах, как человек.

Где: `nexus/data/flywheel.py`, `nexus/data/ingest.py` (поле `text`).

### Канал 2 — физика как числа на общей шине (флаг `--physics`)

Текст — плохой способ передать число: «350» дробится на токены и его величина
теряется. Поэтому каждому токену можно прицепить **вектор инвариантов**:

```
invariants = [x, y, z (м), масса (кг), Fx, Fy, Fz (Н)]
```

Он проходит через линейный слой и складывается с эмбеддингами — модель видит
нагрузку как величину, а не как строку символов.

```bash
nexus train-lm --source jsonl:artifacts/ingest/dataset.jsonl --physics
```

Проверено тестом: при одинаковом тексте, но разной массе и нагрузке предсказания
модели отличаются. Где: `NexusEngine.forward(invariants=…)`, `nexus/bus.py`,
`PhysicsLMDataset`.

### Канал 3 — физика как награда (фаза RL)

Здесь физика становится целью, а не подсказкой:

```
+1.0   код компилируется
+1.5   деталь manifold и технологична (стенки, свесы, доступ фрезы)
+2.0   запас прочности ≥ требуемого
−штрафы  перевес, тонкие стенки
```

Модель генерирует деталь → движок считает → награда. Никакой другой модели-судьи,
только расчёт. Где: `nexus/training/rewards.py`, `nexus/training/grpo.py`.

### Канал 4 — физика как фильтр данных

В корпус попадает только то, что прошло проверку: `nexus ingest` и
`nexus collect` отбраковывают некомпилируемое и записывают причину в
`rejects.jsonl`. Данные самоочищаются — модель не учится на сломанных примерах.

### Что пока не работает

FNO-критик внутри латентного цикла (быстрая прикидка прочности «в уме») —
реализован, но не обучен, поэтому сейчас ничего не даёт. Абляция это
подтверждает: вариант без латентного цикла не хуже. Обучается он командой
`nexus train-fno` после накопления полей напряжений.

## 2. Надо ли чистить базу от кривых моделей?

**Из базы удалять ничего не нужно.** Фильтрация делается на этапе импорта, и
«кривые» модели полезны — но по-другому.

| Что делать | Почему |
| :-- | :-- |
| **Не удалять из БД** | `nexus ingest` сам отбирает валидное; исходники пригодятся при смене критериев |
| **Смотреть `rejects.jsonl`** | это готовый список сломанных моделей на сайте с текстом ошибки |
| **Использовать брак как обучающий сигнал** | пара «сломанный код → замечание → исправленный код» учит модель чинить ошибки, а этого нет ни в одном датасете |
| **Пометить статусом** | если поставить статус вроде `битая`, потом можно фильтровать: `--statuses "готово,в работе"` |

Единственное, что стоит почистить прямо в базе — **точные дубликаты** (одна и та
же деталь, сохранённая много раз). Но и это делает импорт: дедупликация по хешу
кода без комментариев и пробелов.

```bash
# посмотреть, что и почему отбраковано
nexus ingest sql:dump.sql --out artifacts/ingest --limit 200
head -5 artifacts/ingest/rejects.jsonl
cat artifacts/ingest/stats.json     # accepted / duplicates / rejected по причинам
```

Если доля `compile_error` большая — это, скорее всего, не ваши модели плохие, а
наш парсер не понимает какую-то конструкцию OpenSCAD. Такие случаи стоит
присылать: каждая починка парсера возвращает в корпус десятки записей.

## 3. Как работает запрос и где в нём физика

### Простая генерация — `/v1/generate`

```
запрос → токенизация → (опционально инварианты) → ядро → токены ответа
```

Физика здесь только та, что модель выучила: она предсказывает код и его
`<fem>`-сводку по памяти. Никакого расчёта в этот момент не происходит.

### Сквозной сценарий — `/v1/design` (то, ради чего всё делалось)

```
  ТЗ пользователя
        │
        ▼
  1. модель генерирует OpenSCAD код
        │
        ▼
  2. движок парсит код → CSG → воксели
        │
        ├── масса, центр масс, тензор инерции
        ├── аудит: manifold, стенки, свесы, доступ фрезы
        └── МКЭ: поле σ, максимальное напряжение, запас прочности
        │
        ▼
  3. награда: компиляция + технологичность + прочность − штрафы
        │
        ▼
  ответ: код + цифры + вердикт
```

```bash
curl -s -X POST localhost:8000/v1/design \
  -d '{"spec":"<task>Кронштейн под 350 Н","material":"alu6061","force":[0,0,-350]}'
```

В ответе три блока: `generation` (что придумала модель), `analysis` (что показал
расчёт), `reward` (сводная оценка). То есть **проверка физикой происходит на
каждом запросе**, независимо от того, насколько хорошо обучена модель. Даже
слабая модель не сможет выдать деталь, которая «не держит», за годную — цифры
приходят рядом с кодом.

### Кто ещё пользуется тем же расчётом

* `/v1/analyze` — проверить чужой готовый `.scad` без всякой генерации;
* MCP-инструменты — то же самое, но вызывает внешняя LLM (Claude/GPT);
* приёмка модели — `scad_compile_rate` в `nexus eval`;
* маховик данных — метки для новых обучающих примеров.

Один и тот же движок обслуживает и обучение, и инференс — поэтому модель учится
ровно на тех критериях, по которым её потом проверяют.

---

## 4. Короткий ответ на все три вопроса

1. **Физика берётся из расчёта, а не из разметки**: движок считает массу и
   прочность для каждой детали и подаёт результат в обучение четырьмя способами —
   текстом, числом на шине, наградой в RL и фильтром данных.
2. **Базу чистить не надо**: импорт сам отбирает валидное, дедуплицирует и
   складывает брак в отдельный файл, который сам по себе полезен.
3. **При запросе физика считается заново**: `/v1/design` генерирует код и тут же
   проверяет его расчётом, возвращая массу, запас прочности и вердикт вместе с
   кодом.
