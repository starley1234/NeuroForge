# Дообучение современной модели (LoRA) на данных NEXUS

Разведка на август 2026: Qwen2.5-Coder действительно устарел. Ниже — что брать
сейчас, что реально влезает в RTX 5060 Ti 16 ГБ и как проверить результат теми
же метриками, что и свою модель.

---

## 1. Какую базовую модель брать

| Модель | Размер | Лицензия | Влезает в 16 ГБ | Комментарий |
| :-- | :-- | :-- | :-- | :-- |
| **Qwen3-Coder 8B** | 8B | Apache-2.0 | LoRA bf16 | лучший баланс для нашей задачи, семейство лидирует по коду |
| **Qwen3 8B** | 8B | Apache-2.0 | LoRA bf16 | если нужен и код, и русский диалог |
| **Mistral Small 4** | ~24B | Apache-2.0 | QLoRA 4-bit | заявлен как «для специализированного дообучения» |
| **Devstral Small 2** | 24B | Apache-2.0 | QLoRA 4-bit, seq ≤ 2048 | сильный агентный кодер, но тесно |
| **Codestral 22B** | 22B | Mistral non-production | QLoRA 4-bit | заточен под FIM/автодополнение, лицензия ограничивает коммерцию |
| GLM-5.2, Kimi K2.x, Qwen3.6-27B+ | 27B…1T | MIT / bespoke | **нет** | нужен сервер, не одна карта |

Практическое правило для 16 ГБ (подтверждается замерами на этой карте):
**LoRA bf16 — до 7–9B, QLoRA 4-bit — до 13–24B, полный файнтюн — до 1.5B.**

Мой выбор для text-to-3d.ru: **Qwen3-Coder 8B, LoRA в bf16**. Apache-2.0 (можно
коммерчески), помещается целиком без квантизации, знает и Python, и русский.

Важная деталь: **MoE-модели (gpt-oss-20b, Qwen3-Next и подобные) в 4-bit QLoRA
сейчас не обучаются** — bitsandbytes не поддерживает; для них только bf16 LoRA,
а это уже не 16 ГБ.

## 2. Подготовка данных

```bash
# из своей базы, маховика и собранных дистилляцией примеров
nexus export-sft \
  --source jsonl:artifacts/ingest/dataset.jsonl \
  --source jsonl:artifacts/collected/dataset.jsonl \
  --source jsonl:artifacts/flywheel/dataset.jsonl \
  --out artifacts/sft
```

Получаются `train.jsonl` / `val.jsonl` в chat-формате:

```json
{"messages": [
  {"role": "system",    "content": "Ты инженер-конструктор…"},
  {"role": "user",      "content": "<task>Кронштейн под 350 Н, алюминий"},
  {"role": "assistant", "content": "```openscad\n…код…\n```\n// расчёт: масса 41.2 г, минимальная стенка 2.40 мм, запас прочности 3.10"}
]}
```

Две вещи, которых нет ни в одном чужом датасете:

* **строка расчёта** в ответе — модель учится заявлять физические свойства
  вместе с кодом;
* **примеры ремонта** — из траекторий `nexus collect` автоматически строится
  пара «замечание расчёта → исправленный код» (`repair_pairs` в статистике).

Отключаются флагами `--no-physics` и `--no-repair`.

## 3. Установка на Blackwell (sm_120)

```powershell
# CUDA 12.8 — для 50-й серии; на CUDA 13.x встречаются проблемы с ядрами
pip install torch --index-url https://download.pytorch.org/whl/cu128
pip install unsloth trl peft transformers datasets accelerate bitsandbytes
```

Unsloth даёт примерно двукратное ускорение на этой карте за счёт своих
Triton-ядер и экономит ~40 % памяти на активациях. Если он не встанет — скрипт
сам переключится на связку PEFT + TRL (медленнее, но работает).

## 4. Запуск обучения

```powershell
python scripts/train_lora.py --data artifacts/sft --preset qwen3-coder-8b `
       --epochs 3 --batch-size 2 --grad-accum 8 --seq-len 4096 --rank 32
```

Параметры по умолчанию подобраны по практике для этой карты:

| Параметр | Значение | Почему |
| :-- | :-- | :-- |
| rank / alpha | 32 / 32 | до ~10k примеров этого достаточно; выше — риск переобучения |
| lr | 2e-4 | стандартный диапазон LoRA |
| эффективный батч | 16 (2 × 8) | наращивать надо grad-accum, а не batch: память ест именно batch |
| эпох | 3 | дальше начинается заучивание, смотрите eval_loss |
| точность | bf16 | родная для Blackwell |
| optim | adamw_8bit | экономит около 1 ГБ |
| checkpointing | unsloth | ~40 % активаций |
| packing | on | короткие примеры упаковываются, обучение быстрее |

Ожидаемый расход VRAM для 8B в bf16 с LoRA: ~13 ГБ. Если словили OOM —
`--seq-len 2048`, затем `--batch-size 1`, затем `--four-bit`.

Экспорт для инференса:

```powershell
python scripts/train_lora.py ... --merge            # слитые веса bf16
python scripts/train_lora.py ... --gguf q4_k_m      # для Ollama / llama.cpp
```

## 5. Проверка: сравнить с большой LLM честно

Дообученная модель подключается к нашему бенчмарку как обычная команда:

```powershell
nexus bench `
  --model "command:python scripts/serve_lora.py --adapter artifacts/lora/adapter" `
  --model "command:<вызов вашей большой LLM>" `
  --prompts real_prompts.txt --out artifacts/bench/lora_vs_llm
```

Сравниваются не догадки, а физика: доля компилируемых деталей, manifold,
запас прочности, масса, время ответа. Тот же мост работает и для сбора данных:

```powershell
nexus collect --teacher command `
  --command "python scripts/serve_lora.py --adapter artifacts/lora/adapter" `
  -n 500 --attempts 3
```

Пороги для перевода трафика — в [PLAN_TEXT_TO_3D.md](PLAN_TEXT_TO_3D.md):
10 % трафика при `compile_rate ≥ 0.9` от уровня большой LLM, 100 % — при паритете.

## 6. Два трека рядом

| Трек | Что | Когда полезен |
| :-- | :-- | :-- |
| **LoRA на Qwen3-Coder 8B** | ваши веса поверх открытой базы, домен и русский язык | результат за вечер, продуктовый путь |
| **Своя архитектура NEXUS** | обучение с нуля, физика в токенах, O(1) память | когда наберётся 300M+ токенов; исследовательский путь |

Инфраструктура общая: реестр версий, приёмочные тесты, `nexus bench`,
физический верификатор. Модель можно менять, конвейер остаётся.

## 7. Частые проблемы

| Симптом | Причина и решение |
| :-- | :-- |
| OOM на старте | `--seq-len 2048`, потом `--batch-size 1`, потом `--four-bit` |
| OOM ближе к концу эпохи | длинные примеры: включите `--seq-len` поменьше, packing уже включён |
| eval_loss растёт со второй эпохи | мало данных: 1 эпоха или больше примеров (`nexus collect`, `nexus ingest`) |
| модель отвечает текстом, а не кодом | системный промпт в `serve_lora.py` должен совпадать с тем, что был в обучении |
| `bitsandbytes` не собирается под sm_120 | обновите bitsandbytes; для MoE-моделей 4-bit не поддерживается вовсе |
| CUDA 13.x странно себя ведёт | ставьте колёса cu128 — для Blackwell это проверенный вариант |
