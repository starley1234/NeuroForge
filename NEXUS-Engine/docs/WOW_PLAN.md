# План на «вау»: что делать с моделью дальше

Шесть шагов, каждый — самостоятельная демонстрация, которую можно показать
пользователю и которая одновременно готовит следующий. Порядок выбран так, чтобы
эффект появлялся раньше, чем закончится обучение модели.

---

## Шаг 1. «Деталь, которая сама себя усиливает» — работает уже сегодня

Реализовано: `nexus optimize`. Берёт любой параметрический шаблон из вашей
библиотеки, крутит **только силовые параметры** (толщины, рёбра, бобышки) и
считает настоящий МКЭ на каждом шаге.

```bash
nexus optimize bracket.scad --force 0 0 -350 --material pla --safety 3.0 --budget 40
```

```
параметр                     было      стало
--------------------------------------------
thickness                       6       4.07
rib                             8       5.69
--------------------------------------------
масса, г                    36.92      24.33   (−34.1 %)
запас прочности             23.00      13.91
вариантов просчитано: 36 за 2.3 с
```

Габариты, отверстия и межосевые расстояния не трогаются — деталь остаётся той,
что просил пользователь.

**Как показать на сайте.** На странице шаблона — второй слайдер:
«нагрузка, Н» и кнопка «подобрать под неё». Деталь перестраивается за секунды,
рядом цифры «масса −34 %, запас 13.9». Это буквально generative design, который
у конкурентов стоит денег и живёт в облаке.

Цена внедрения: один вызов API, полдня работы. Отдача: фича, которой нет ни у
Zoo, ни у AdamCAD, ни у Fusion в бесплатной версии.

## Шаг 2. «Модель, которая чинит свои ошибки» (2–3 недели)

Механика уже есть в `nexus collect`: генерация → проверка → замечание → повтор.
Осталось вывести её в интерфейс.

```
Пользователь: «крючок для полотенца под 5 кг»
  → генерация
  → ⚠️ стенка 0.9 мм, запас 0.7 — не выдержит
  → автоматическая переделка
  → ✅ стенка 2.4 мм, запас 2.3, масса 18 г
```

Показывать обе версии: «первая попытка» и «после проверки». Это одновременно:

* самый убедительный демо-ролик из возможных;
* поток данных «сломано → исправлено», которого нет ни в одном датасете;
* готовый материал для RL-фазы.

## Шаг 3. Своя модель в проде через роутер (4–8 недель)

Не «заменить большую LLM», а **отобрать у неё простые классы запросов**.

```bash
nexus bench --model "command:<большая LLM>" --model "command:python serve_own.py" \
            --prompts real_prompts.txt --out artifacts/bench/round1
```

| Класс запросов | Доля трафика | Кто обслуживает после шага 3 |
| :-- | --: | :-- |
| клипсы, заглушки, шайбы, держатели, простые крепления | ~60 % | своя модель |
| корпуса, переходники, кронштейны | ~30 % | своя модель после дообучения |
| редукторы, ЖРД, купола, всё с расчётами по ГОСТ | ~10 % | большая LLM |

Эффект: себестоимость генерации падает в разы, скорость растёт (локально, без
сети), а зависимость от чужого API исчезает для основной массы запросов.

## Шаг 4. «Сфотографировал сломанную деталь — получил модель» (2–3 месяца)

Ваша самая популярная тема — автомобильные клипсы и заглушки. Сценарий:
пользователь фотографирует сломанную деталь и линейку, получает параметрическую
модель со слайдерами.

Что для этого уже готово: `nexus render-dataset` делает выборку «6 ракурсов ↔
код ↔ параметры ↔ физика» из вашей же базы. Архитектура позволяет заморозить
ядро и обучить только визуальный энкодер:

```python
model.freeze_core()
model.register_encoder("image", VideoSSMEncoder(model.cfg.d_latent))
```

Сначала «рендер → код» (данные есть), потом дообучение на реальных фото от
пользователей (кнопка «загрузить фото детали»).

## Шаг 5. Публичный бенчмарк как репутация (параллельно, 2–4 недели)

Никто в мире не меряет CAD-генерацию по физике: все считают геометрическое
сходство. Сделайте первый такой бенчмарк и опубликуйте:

* **PhysCAD-Bench**: 300 реальных инженерных запросов + метрики
  «компилируется / manifold / печатается без поддержек / держит нагрузку»;
* открытый лидерборд, куда можно прогнать GPT, Claude, Qwen, Zoo, AdamCAD;
* всё уже считается командой `nexus bench` — нужен только сайт с таблицей.

Что это даёт: цитируемость, входящий трафик от разработчиков, фиксацию
приоритета (важно для патентной защиты) и позицию «мы задаём стандарт качества
в этой области», независимо от того, чья модель победит.

---

## Шаг 6. Офлайн-коробка для предприятий (3–6 месяцев)

Единственное, что облачные конкуренты не могут предложить в принципе:

```
docker compose up -d      # модель + движок + API в закрытом контуре
```

Чертежи не покидают периметр, интернет не нужен, лицензия не привязана к
подписке. Для оборонных, приборостроительных и просто осторожных предприятий это
решающий аргумент. Технически всё уже есть: Dockerfile, API с ключом, реестр
версий, приёмочные тесты.

## Что делает это «вау» в глазах пользователя

| Обычный text-to-CAD | Ваш продукт после этих шагов |
| :-- | :-- |
| «вот модель, надеюсь, подойдёт» | «модель выдержит 350 Н, весит 24 г, печатается без поддержек» |
| не подошло — пиши заново | не подошло — система сама переделала и показала, что изменила |
| статичный STL | живые слайдеры + автоподбор под нагрузку |
| работает, пока есть подписка и интернет | работает у вас на сервере, веса ваши |
| качество «на глаз» | цифры и открытый бенчмарк |

## Порядок и сроки

| Когда | Что | Результат |
| :-- | :-- | :-- |
| Неделя 1 | физический бейдж + `nexus optimize` на страницах шаблонов | видимая фича, отличие от всех |
| Недели 2–3 | логирование процесса, кнопки обратной связи, авторемонт | поток уникальных данных |
| Недели 4–8 | своя модель + роутер по классам запросов | себестоимость и независимость |
| Месяцы 2–3 | PhysCAD-Bench, публикация, приоритет | репутация и защита |
| Месяцы 3–6 | фото → деталь, офлайн-коробка | новые рынки |

Ключевая мысль: **вау создаёт не размер модели, а гарантия**. «Эта деталь
выдержит» — фраза, которую сегодня не может сказать ни один text-to-CAD сервис,
и она у вас уже считается.
